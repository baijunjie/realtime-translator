# agreement 管线翻供修复（2026-07-22）

CER 评测基建（[asr-eval](asr-eval.md)）上线首日暴露：sense-voice × ja 用例 `pipeline`
CER 47~49% 而 `offline` 仅 0.8%。逐 tick 探针（临时脚本驱动 core 管线 + 日志包装引擎）
定位为**「模型随窗口增长合法改写已出前缀（翻供）」×「前缀单调稳定假设」**的三个叠加缺陷。
2026-07-04 范式的「senseVoice 增长窗口下解码前缀单调稳定（探针实证）」结论**已被证伪**：
み↔皆 表记改写、读点插入、ITN 数字改写（八十→80）都是常态。

## 三个缺陷与对应修复（均在 core `transcription-pipeline.ts`）

1. **翻供卡死提交**：已提交「みなさん、こんにちは」后模型整体改写为「皆なさん…」，
   旧实现要求 agreed 以已提交前缀开头才落定 → 从此永远无法提交，最终停滞保护把整段
   未提交音频丢弃（实录丢了「の進捗状況を確認します。開発」）。
   **修复：翻供重基**——agreed（连续两次解码一致的前缀）比 committedInWindow 更长即
   落定，不再要求前缀关系；坍缩型翻供（输出变短）天然不满足「更长」仍被拒绝；
   已滑出窗口的 committedDone 永不回退。
2. **定稿弃尾丢整句**：断行定稿的 tail 解码只要不以已提交前缀开头就整个丢弃（原设计
   针对坍缩保底），而 tail 常常只是改写了表记（少个读点）却覆盖了完整整句——实录整句
   「本日はお忙しい中…」被丢。**修复：定稿择长**——tail 与前缀不一致时取二者中更长者
   （坍缩 tail 更短，保底逻辑不变）。
3. **滑动对齐错位产生重复/乱码**：alignCommitted 原按码点数硬对齐 committed 与 tokens，
   ITN 让 text（80%）与 tokens（八十パーセント）表面脱节时切点落在错误音频位置，
   实录「80率は80%」重复。**修复：标点容忍的逐字对齐**——committed 侧标点/空白可跳过
   （text 里的标点是模型补的，tokens 没有），真正表面分歧（ITN）在分歧 token 处停止，
   绝不硬切；完全对不上则本 tick 不滑动。
   配套**停滞保护分流**：新增 noAdvanceTicks（有提交进展但窗口滑不动，如 ITN 区域
   持续阻断对齐）；该型停滞把窗口直接前移到 now（只丢 1~2 tick 未提交尾巴），不能沿用
   no-progress 型的 now-4s（保留已提交音频会被重解码 → 重复定稿，实测踩过）。

## 结果（TTS 冒烟，eval-cer）

ja `pipeline` 47.2%→10.6%（`offline` 0.8%）；zh 1.1%、en 3.3% 无回归；reazon chunk
路径不受影响（22.8% 不变）；sense-voice 三用例加权 20.2%→5.0%。残余差距主要是
ITN 表记噪声（80% vs 八十パーセント，且 ITN 行为随窗口长度变化）与模型读法怪癖
（皆なさん）。单测同步改写：原「agreement 滑动守卫」测试编码的旧语义（翻供一律拒绝）
已由「翻供重基」两用例取代；新增定稿择长用例。

**Why:** 「前缀单调稳定」是 2026-07-04 范式的隐含地基，被证伪后这三处都是结构性丢字根源；
记录下来避免以后有人把重基/择长又改回「严格单调」。
**How to apply:** 遇到 agreement 模型丢整句/文本重复，先怀疑翻供路径（探针照抄本次思路：
包装 engine.transcribe 打印每 tick 窗口与输出）；ITN 与流式提交天然相性差，若未来数字区
问题变多，可评估「管线解码关 ITN、定稿时再做文本级 ITN」的方案；改这些逻辑必须
先跑 `eval-cer` 留基线。
